## 1. 프로젝트 개요

### 1.1 비전
MD/영양사/바이어 전용 AI 대시보드 및 챗봇 시스템으로, 농수산물·원자재·식자재 가격 데이터와 뉴스를 결합하여 급식 메뉴 단가를 최적화하는 서비스.

### 1.2 대상 사용자
- **영양사**: 급식 메뉴 계획, 식자재 주문, 레시피 원가 관리
- **MD(Merchandiser)**: 전략 상품 기획, 공급업체 가격 협상, 매입가 결정
- **바이어**: 도소매 시세 분석, 구매 의사결정

### 1.3 핵심 가치 제안
- 실시간 시세 추적 및 이상치 감지로 선제적 의사결정 지원
- 검색어 트랜드 API를 활용한 실시간 및 글로벌 시장 동향 이슈 모니터링
- AI 기반 대체 식자재 및 레시피 추천으로 원가 절감
- 뉴스 기반 시장 컨텍스트 제공으로 가격 변동 원인 파악
- 다양한 데이터 소스를 활용한 온톨로지 구성
- 원자재 데이터 기반으로 AI를 활용한 메뉴 및 레시피 자동 제안

## 2. 기능 요구사항 (Functional Requirements)

### FR-01: 식자재 분류 체계 대시보드
- **설명**: 농/수산물, 원자재, 식자재를 계층적 분류 체계로 분류하여 필터링 조회
- **분류 카테고리**: 구황작물, 수산물, 채소류, 과일류, 축산류, 가공식품 등
- **데이터 표시**: 도매가, 소매가, 시세 갭(Gap) 분석
- **인터랙션**: 카테고리 탭 전환, 필터링, 정렬

### FR-02: 시세 추이 그래프 및 가격 이상치(Spike) 뉴스 매핑
- **설명**: 농축수산물 시세 조회/추이 분석 그래프 구현
- **Spike 감지**: 가격 이상치 발생 시점 자동 감지
- **뉴스 매핑**: Spike 시점에 마우스 오버 시 관련 뉴스 헤드라인 + URL 표시
- **차트 라이브러리**: Recharts (CustomTooltip 활용)

### FR-03: AI 기반 메뉴/레시피 제안 및 식수별 비용 시뮬레이션
- **설명**: AI가 메뉴, 재료, 레시피를 제안하고 식수별 원가 계산
- **식수 입력**: 100식, 1,000식, 10,000식 등 사용자 입력 기준
- **출력**: 레시피별 재료 목록, 단가, 총 원가, 영양 정보

### FR-04: 대체 식자재 원가 절감 전략 제안
- **설명**: 레시피별 대체 가능한 식자재를 제안하고 원가 절감 효과 시뮬레이션
- **트리거**: 특정 식자재 가격 급등 시 자동 제안 또는 사용자 요청
- **출력**: 대체 식자재 목록, 가격 비교, 절감률, 대체 레시피

### FR-05: 대화형 AI 챗봇 (RAG 기반)
- **설명**: MD/바이어/영양사가 현재 가격 동향 및 이슈를 질의할 수 있는 챗봇
- **기반 기술**: Amazon Bedrock Knowledge Bases (RAG), Backend 기술은 FastAPI는 Lang chain 구현
- **데이터 소스**: 뉴스 데이터 + 서비스 온톨로지 + 시세 데이터
- **UI**: 플로팅 챗봇 (우측 하단, 타이핑 애니메이션)

### FR-06: 뉴스 크롤링 및 연동
- **대상**: 네이버 뉴스 검색 API + 농림축산식품부/해양수산부 공식 보도자료, 공공데이터포털(6~7개 API 호출)
- **처리**: 식자재 관련 키워드 필터링, 시세 이벤트와 시간 매핑
- **저장**: 뉴스 기사는 벡터 임베딩으로 RAG Knowledge Base에 적재, 뉴스에 대한 이벤트는 시계열DB 혹은 RDB, 나머지는 RDB

## 3. 비기능 요구사항 (Non-Functional Requirements)

### NFR-01: 성능
- 대시보드 초기 로딩: 3초 이내
- 차트 데이터 렌더링: 1초 이내
- 챗봇 응답 시간: 5초 이내 (스트리밍 응답)

### NFR-02: 가용성
- 시연 환경: 로컬 개발 서버 (localhost)
- 프로덕션 설계: AWS 기반 고가용성 아키텍처 (문서화)

### NFR-03: 보안 (Security Baseline Extension 적용)
- SECURITY-01 ~ SECURITY-15 전체 적용
- API 키 관리: AWS Secrets Manager 또는 환경 변수
- 입력 검증: 모든 API 엔드포인트에 스키마 검증
- HTTPS 강제 (프로덕션 환경)

### NFR-04: 테스팅 (Property-Based Testing Extension 적용)
- PBT-01 ~ PBT-10 전체 적용
- 프레임워크: Hypothesis (Python), fast-check (TypeScript)
- 라운드트립 테스트: 직렬화/역직렬화, API 요청/응답
- 불변성 테스트: 가격 계산 로직, 분류 체계 무결성

### NFR-05: 확장성
- 데이터 소스 추가 용이한 어댑터 패턴
- 새로운 식자재 카테고리 추가 가능한 유연한 분류 체계
- 다국어 지원 가능한 구조 (향후)

### NFR-06: 사용성
- Bento-box 레이아웃의 모던 대시보드
- 반응형 디자인 (데스크톱 우선)
- 직관적 네비게이션 및 필터링

## 4. 기술 스택 결정사항

| 레이어 | 기술 | 근거 |
|--------|------|------|
| **프론트엔드** | Next.js 14 + React + TypeScript | 요구사항 명시, SSR/SSG 지원 |
| **UI 프레임워크** | Tailwind CSS | Bento-box 레이아웃, 빠른 스타일링 |
| **차트** | Recharts | 요구사항 명시, CustomTooltip 지원 |
| **백엔드** | Python (FastAPI) + LangChain | AI/ML 라이브러리 활용 용이, LLM 오케스트레이션 |
| **AI/LLM** | Amazon Bedrock (Claude) | 사용자 선택 |
| **RAG** | Amazon Bedrock Knowledge Bases + LangChain | 관리형 서비스 + LangChain 체인 구현 |
| **RDB** | Amazon RDS (PostgreSQL) | 시세 이벤트, 식자재 마스터, 분류 체계 저장 |
| **온톨로지** | Amazon Neptune (그래프 DB) | 완전한 지식 그래프 구현 |
| **데이터 소스** | KAMIS API + 공공데이터포털 + Naver (검색API, 데이터랩 (검색어트렌드)) + 크롤링 | 실제 API + 크롤링 병행 |
| **뉴스** | 네이버 뉴스 API + 정부 보도자료 | 다중 소스 혼합 |
| **배포(시연)** | localhost (개발 서버) | 해커톤 시연 환경 |
| **배포(설계)** | AWS (ECS, CloudFront, RDS 등) | 프로덕션 아키텍처 문서화 |

## 12. 역질문 (팀에게 제안하는 질문)

### 12.1 역할 분담 관련
1. **풀스택 팀원 D의 우선순위**: 크롤링 구현과 프론트-백 연동 중 어느 쪽에 더 시간을 투자할까요? 크롤링이 실패하면 Mock 데이터로 전환할 타이밍은?
2. **AI/데이터 팀원 C**: Neptune 온톨로지 구축에 시간이 많이 소요될 수 있습니다. 최소한의 관계 데이터(JSON)로 시작하고 Neptune은 아키텍처 문서로만 제시하는 것은 어떨까요?

### 12.2 크롤링 대상 한정
3. **크롤링 범위 축소 제안**: 6시간 내 안정적 시연을 위해, 크롤링 대상을 "네이버 뉴스 API (농산물/수산물 키워드)"로 한정하고, 정부 보도자료는 샘플 데이터로 대체하는 것은 어떨까요?
4. **KAMIS API 응답 속도**: KAMIS API가 느리거나 불안정할 경우를 대비해, 사전에 1주일치 데이터를 캐싱해두는 전략은?

### 12.3 AI 환각 통제
5. **Bedrock Knowledge Bases 구축 시간**: KB에 적재할 문서를 미리 준비해야 합니다. 최소한 어떤 문서를 넣을 건지 (시세 데이터 CSV? 레시피 JSON? 뉴스 텍스트?) 우선순위를 정해야 합니다.
6. **챗봇 응답 범위 제한**: "모르겠습니다"라고 답하는 경계를 명확히 설정할까요? (예: 시세 데이터가 없는 품목에 대한 질문)

### 12.4 시연 전략
7. **시연 시나리오 사전 준비**: 심사위원에게 보여줄 3~4개의 핵심 시나리오를 미리 스크립팅하고, 해당 시나리오에 필요한 데이터를 확실히 준비하는 것이 좋습니다. 어떤 시나리오를 선택할까요?
8. **Fallback 전략**: 실시간 API가 실패할 경우 자동으로 캐시된 데이터로 전환하는 로직을 넣을까요?
